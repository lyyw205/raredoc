# card-check — 카드 DB 존재 확인 + 실존 리서치

사용자가 언급한 카드가 (1) 우리 DB에 있는지, (2) 없다면 현실에 실존하는 카드인지, (3) 실존한다면 표기 차이 때문에 DB에서 못 찾은 것은 아닌지 차례로 확인해서 결론을 보고한다.

핵심 원리: **1차 DB 검색이 실패해도 "DB에 없다"고 단정하지 않는다.** 사용자의 표기(언어·별명·음차)와 DB 저장 표기가 다를 수 있으므로, 리서치로 정식 명칭(ja/ko/en)·세트·번호를 확보한 뒤 그 식별자로 DB를 한 번 더 검색해야 정확한 결론이 나온다.

## 분기: 트레이너/아이템 KR 정합 (별도 모드)

제보가 "이 카드 있어?"가 아니라 **트레이너/도구/스타디움/에너지 카드의 KR 연결·표기·이미지가 잘못됐다**는 신호면(이름이 바뀐 듯·일러가 반대·swap·이미지 깨짐), 아래 일반 워크플로 대신 **`references/kr-trainer-alignment.md` 를 읽고 그 절차를 따른다.**

이게 중요한 이유: KR 한국판은 트레이너를 가나다순으로 재정렬하는데 사전(`TR_JA2KO`) 누락이 있으면 그 세트 트레이너 블록이 **통째로 어긋난다**. 그래서 **한 장 제보는 거의 항상 수십 장 스크램블의 일각**이다. 제보된 카드만 고치지 말고, 번들 스크립트로 그 세트 트레이너 전체를 전단사 감사한다:

```bash
npx tsx .claude/skills/card-check/scripts/audit-kr-trainers.ts --jp <jpSetId> --kr <krSetId>
```

(자세한 진단 분기·사전 보강·이미지 검증·교정·커밋 절차는 전부 그 reference 에 있다. 여기서 길게 반복하지 않는다.)

## 워크플로

### 0. 입력 해석

지시에서 카드 단서를 추출한다: 카드명(언어 불문), 세트/팩명, 콜렉션 번호, 레어도, 도감번호. 카드가 여러 장이면 각각 독립적으로 아래 과정을 수행하고 마지막에 표로 합쳐 보고한다.

### 1. DB 1차 검색

번들 스크립트를 레포 루트에서 실행한다 (DB는 Supabase, .env 자동 로드):

```bash
npx tsx .claude/skills/card-check/scripts/search-card.ts "<카드명>" [--set <세트코드|세트그룹ID>] [--num <번호>] [--dex <도감번호>] [--limit 30]
```

- 카드명은 부분일치·대소문자 무시로 CardLocale.name(전 언어) + LogicalCard.nameKo + CardText.name을 한 번에 검색한다.
- 결과 JSON에는 매치별 세트그룹·지역별 로케일(세트/번호/이름)·레어도가 들어 있다.
- 변형도 시도해볼 것: 공백 제거/추가("메가리자몽ex" ↔ "메가리자몽 ex"), 조사 제거, ex/EX/GX 분리.
- 세트가 지정된 질문("X팩에 Y 있어?")이면 매치의 setGroup이 그 팩인지를 봐야 한다 — 다른 팩에서만 발견되면 "그 팩에는 없음, 다른 팩에 있음"이 정답이다.

찾았으면 5단계 보고로 직행. 못 찾았거나 애매하면(동명 카드 다수 등) 2단계로.

### 2. 리서치 — 실존 여부 확인

`references/research-sources.md`를 읽고 거기 적힌 검증된 방법대로 공식 사이트를 조회한다. 순서:

1. **KR 공식** (pokemoncard.co.kr) — 한국어 이름일 때 1순위. AJAX 검색.
2. **JP 공식** (pokemon-card.com) — 일본어 이름이거나 KR에서 못 찾을 때. resultAPI 키워드 검색. ⚠️ 응답이 NFD 분해 가나이므로 NFC 정규화 필수.
3. **EN 공식** (pokemon.com) — 영어 이름일 때. ⚠️ Incapsula 봇차단: 단건 요청만, 응답 <5KB면 차단된 것.
4. **보조 소스** — 공식에서 안 나오면 tcgdex API, limitlesstcg 등으로 폴백 (구세대·프로모에 유리).

리서치에서 확보할 것: **실존 여부**, 정식 명칭(가능한 언어 전부), 수록 세트(코드), 콜렉션 번호, 레어도, 도감번호. 이름이 음차/별명이었다면 정식 표기가 무엇인지가 가장 중요한 수확이다.

신팩 시크릿 카드는 JP 공식 검색 DB에 늦게 등재될 수 있다 — 검색에 없어도 특설페이지(`/ex/{세트}/assets/json/cardlist.json`)에 먼저 공개되는 경우가 있으니 신팩이면 그것도 확인한다.

### 3. DB 2차 검색

리서치에서 얻은 식별자로 1단계 스크립트를 다시 돌린다. 이번에는:

- 정식 명칭 각 언어(특히 일본어 원명) → `"<ja명>"` 검색
- 도감번호 → `--dex N` (이름 표기가 전부 달라도 종이 같으면 잡힌다)
- 세트코드 + 번호 → `--set <코드> --num <번호>`

여기서 발견되면 "DB에 있음 (단, 사용자 표기와 DB 표기가 다름)"이 결론이고, 어떤 표기로 저장돼 있는지 알려준다. 여전히 없으면 "실존하지만 DB 미수집"이 결론이다.

### 4. 판정 불가 처리

리서치로도 실존 여부가 불분명하면(공식·보조 모두 무응답) 솔직하게 "확인 불가"로 보고하고, 어떤 소스를 어떻게 조회했는지 남긴다. 추측으로 "없다"고 단정하지 않는다.

### 5. 결과 보고

카드별로 아래 4분면 중 하나로 결론을 내고 증거를 붙인다:

| | 실존함 | 실존 안 함 / 불명 |
|---|---|---|
| **DB 있음** | ✅ 정상 — 세트·번호·지역 제시 | ⚠️ DB 데이터 의심 — 검증 제안 |
| **DB 없음** | 🔴 수집 누락 — 수집 제안 | ❌ 존재하지 않는 카드 — 유사 카드 제시 |

보고에 반드시 포함:
- 카드별 결론 한 줄 + 4분면 위치
- DB에 있으면: 세트그룹, 지역별 로케일(세트/번호), 레어도, logicalCardId
- 리서치를 했으면: 어떤 소스에서 무엇을 확인했는지 (URL 또는 식별자)
- 1차에서 못 찾고 2차에서 찾았으면: 표기 차이가 무엇이었는지
- 다음 액션 제안 (수집 필요 / 데이터 교정 필요 / 없음)

여러 장 질문이면 카드 × (DB 상태, 실존, 결론) 표로 정리한다.

### 6. 최종 직접 점검 — DB를 수정했다면 필수

연결·교정·병합 등 **DB를 변경한 경우**, 스크립트 출력을 믿지 말고 보고 전에 직접 재검증한다. (근거: 병합 직후엔 항상 숨은 오배정이 나왔다 — rankZip 동점 교차 §24, 본문↔SIR 스왑 §29, Charcadet 스왑 §30)

1. **제보 목록 항목별 재조회** — 사용자가 제보한 카드 번호 전수를 DB에서 다시 읽어 최종 연결 상태(어느 JP와 연결됐는지)를 집계해 보고에 표로 포함한다. 트레이너/아이템 KR을 고쳤다면 `audit-kr-trainers.ts`를 **--apply 없이** 다시 돌려 그 세트 오링크가 0인지(멱등) 확인한다.
2. **세트 전수 일러 감사** — EN 세트 전체를 권위 소스 artist와 대조해 불일치를 찾는다. ptcg.io가 artist를 제공하면 그것으로, 미제공 세트(sv7/sv8/sv8pt5/me1/me3 등)는 tcgdex(`sv0X-NNN` 3자리 패딩 localId)로. (전수 스윕은 서드파티로 — pokemon.com은 대량 요청 불가)
3. **불일치는 이미지 직접 판정 + EN 개별 최종 검증은 pokemon.com 공식** — tcgdex/ptcg.io도 일러 오기가 있다(이브이 시리즈, Petrel/Proton 교차). 표기 불일치만으로 재배정하지 말고 카드 이미지를 받아 눈으로 대조한 것이 최종 권위. HP·기술명까지 다르면 별개 카드 확정. **개별 EN 카드의 최종 판정(연결 확정·오연결 교정 전)은 pokemon.com 공식 상세 페이지를 단건 조회**해 이미지·표기를 확인한다 — 봇차단은 연속 대량 요청에만 걸리므로 단건(요청 간 딜레이, 응답 <5KB면 차단 → 잠시 후 재시도)은 가능. 서드파티끼리 엇갈릴 때 공식이 심판.
4. **빌드 JSON 카운트 확인** — 재빌드 후 counts(enMatched/enOnly/krMatched)가 기대값과 일치하는지, 잔류 카드들이 전부 사유 확정 상태인지 확인한다.

## 주의

- 스크립트 실행은 반드시 레포 루트에서 (`dotenv`가 루트 .env를 읽는다).
- 같은 카드가 여러 세트에 있을 수 있다(재録). 사용자가 세트를 지정했으면 그 세트 기준으로 답하고, 다른 세트 존재는 부가 정보로.
- 시크릿/패럴렐(예: 113/081 SAR)은 베이스 카드와 별개 행이다 — 레어도까지 맞는지 확인.
- 리서치 요청 횟수는 최소한으로 — 각 소스 1~2회 조회로 충분하다. EN 공식은 연속 요청 금지.
